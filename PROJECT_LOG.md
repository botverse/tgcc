## 2026-09-17 — real `~/.tgcc/config.json` corruption risk in the test suite (merged)

`tests/repo-management.test.ts` (added `fe3d389`, Feb 2026) read and wrote `src/config.ts`'s `CONFIG_PATH` — a module-level constant that resolves to the real `~/.tgcc/config.json` — with no sandboxing at all: its `updateConfig` tests backed up whatever config existed on the host running the tests, mutated it with throwaway repo entries, and restored the backup afterward. Every `pnpm test`/`npm test` run on any developer machine has therefore been reading and overwriting the live config (holding all 13 real bot tokens) since February — safe only as long as the backup/restore pair completed without a crash mid-write or without racing the live `tgcc` systemd service's own writes to the same file. Same class of risk as the `systemd-unit-tracking` incident below, this time on the config file rather than the unit file. Discovered while verifying an unrelated feature branch (`agent-conversation-monitor`)'s final test gate: the integration lead noticed the real file's mtime moving during that gate's test runs, with no corresponding `tgcc.service` log activity to explain it, and asked for the actual cause to be found rather than assumed — it was pre-existing, not introduced by that feature or its tests, confirmed file-by-file rather than assumed.

Fixed with two layers: `vitest.config.ts` now sandboxes `HOME` to a fresh, disposable directory via `test.env`, applied before any test module — and therefore any module-level constant like `CONFIG_PATH` — is imported, so the protection is structural rather than per-file; `tests/repo-management.test.ts` itself now seeds a throwaway config into the (now-sandboxed) path instead of depending on or risking a real one. Verified: real `~/.tgcc/config.json` mtime (`1789662338` / `2026-09-17 17:25:38.343185495 +0100`) unchanged across full `pnpm test` runs on both the originating feature branch (398 passed / 1 skipped) and this fix's own `main`-based branch (259 passed / 1 skipped, the pre-monitor-feature baseline) — checked before, and repeatedly after, on each. Mutation-checked by temporarily disabling the fix while an independent, external safety net protected the real file throughout, confirming the fix is the active protective layer rather than a no-op.

Integrated via [PR #7](https://github.com/botverse/tgcc/pull/7), merge commit `9199534`, merged 2026-09-18. Cherry-picked from `feat/agent-conversation-monitor`'s `60d17e7` so the fix could land independently of that feature's review and deployment, since every test run on `main` kept rewriting the live config until it did. This records integration only: the guard is present on `main` and verified by the real config's mtime holding across full test runs, and nothing here changes runtime behaviour.

## 2026-09-17 — conversation monitor implemented (PROPOSAL — branch-verified, not yet merged)

**This entry describes work on `feat/agent-conversation-monitor`, prepared as part of that PR. It is not yet integrated — do not read it as a statement about `main`.** Colleagues use TGCC agents directly, some of which can take destructive actions on real systems, with no owner visibility into those conversations. Added a `ConversationMonitor` (`src/monitor.ts`) that mirrors every monitored agent's turns — inbound messages (Telegram DM/group/voice-transcription/photo/document), thinking, tool calls (input included, destructive patterns flagged ⚠️), tool results, and replies — into a Telegram destination (one forum topic per agent), except turns originating from the owner. Off by default: absent `monitor` config block in `~/.tgcc/config.json` leaves behavior unchanged, confirmed by the full pre-existing `npm test` suite (259 passed / 1 skipped / 0 failed, all 17 files) staying green against the changed `bridge.ts`/`telegram.ts`/`config.ts`, none of whose existing call sites pass a `monitor` block. Secret redaction (AWS/OpenAI/GitHub/Slack keys, JWTs, PEM blocks, generic `*_KEY=`/`*_SECRET=`/`*TOKEN=`/`*PASSWORD=` assignments) and destructive-pattern flagging (`rm -rf`, `git push --force`, `DROP TABLE`, unguarded `DELETE FROM`, `docker rm`/`system prune`, `systemctl stop`, `chmod -R 777`, credential-file writes, etc.) each live in one dedicated module (`monitor-redact.ts`, `monitor-destructive.ts`) so the pattern lists can grow.

Verified on branch `feat/agent-conversation-monitor` (not `main`): `pnpm run build` clean; full existing `pnpm test` green as above; scratch harnesses (never committed — `tests/` is left for the tester) exercising every named redaction/destructive pattern plus the `ConversationMonitor` public surface against a mocked Telegram sender, covering all 13 acceptance criteria in `work/agent-conversation-monitor/PLAN.md` to the extent possible without a real Telegram destination (no live Telegram calls were made, per the task's operational constraints). Two things explicitly **not** verified here: the real grammy `createForumTopic`/`message_thread_id` API surface (confirmed by reading its type definitions, not by a live call), and `/monitor_here` against a real bot/config (would have touched the real `~/.tgcc/config.json`, off-limits during development). **Not reviewed, no dedicated regression suite in `tests/` yet, not deployed.**

**Update, same day, after a lead review:** three problems were found and fixed before bringing in a tester — (1) the original delivery design (one Telegram message per assistant `message_stop`) didn't hold up against Telegram's real ~20 messages/minute-per-chat limit shared across every monitored agent's topic; delivery is now a single pump loop per destination chat that packs pending content into as few messages as fit, prioritizes destructive/inbound/reply content ahead of routine content on every send, and caps+collapses routine backlog — still purely event-driven, no new timers. (2) `/monitor_here` had no real authorization check (gated only by whichever bot's own generic `allowedUsers`, which for `sentinella` includes the colleagues the monitor exists to watch); it's now wired up only on the supervisor's bot and requires the caller's Telegram user id to match a new required `monitor.ownerUserId` config field, checked via a pure exported function. (3) the monitor destination chat itself was never excluded from being treated as a conversation, so anything the owner typed there was spawned as a CC prompt inside the mirror feed — now ignored except for `/monitor_here` and a read-only `/status`. Acceptance criterion 10 was revised and criteria 12–13 added to match; see `work/agent-conversation-monitor/PLAN.md`'s 2026-09-17 revision note and `LOG.md`'s "lead review: 3 fixes" entry for the full account. Re-verified after all 3 fixes: `pnpm run build` clean, `pnpm test` still 259 passed / 1 skipped / 0 failed.

**Update, 2026-09-18, final reconciliation before owner review:** two further lead-review rounds found and fixed a DM-destination lockout bug (a private-chat monitor destination collided with every agent's private-chat id, since Telegram private-chat ids equal the user's id and are identical across every bot — fixed by scoping the monitor-chat exclusion to group destinations on the supervisor's own bot only) and confirmed (no change needed) that the delivery pump's `⚠️` priority is already correctly destination-chat-wide, not just per-agent. A dedicated tester (`monitor-tests`) then wrote a full `tests/` regression suite (`monitor.test.ts`, `monitor-auth.test.ts`, `monitor-bridge.test.ts`, `monitor-destructive.test.ts`, `monitor-redact.test.ts` — 5 files, 398 tests) against all 14 acceptance criteria and found two real redaction gaps during an exhaustiveness pass — JSON/dict-quoted secret keys (`{"apiKey": "..."}`) and connection-string embedded passwords plus opaque Bearer tokens — both fixed and re-verified by the tester, who also mutation-tested the authorization check, the monitor-chat exclusion, and the redaction rules specifically to confirm the suite catches regressions there, not just exercises the happy path. Branch reconciled with `main` at `9199534` (this log's own `test-home-sandbox` fix above, merged via PR #7 — the feature branch had already carried the identical fix independently since `60d17e7`, so the merge was a content no-op for `vitest.config.ts`/`tests/repo-management.test.ts`). Verified on the merged result: `pnpm run build` clean, full `pnpm test` green, real `~/.tgcc/config.json` mtime unchanged across the run. Full account of every round: `work/agent-conversation-monitor/LOG.md`.

Next: PR #6 is now open (no longer draft) for the owner's review; deployment (create the destination supergroup, add a `monitor` config block with `ownerUserId` set, restart `tgcc`, run `/monitor_here`) is a separate authorized step after merge, per `work/agent-conversation-monitor/PLAN.md` § Deployment. Details: `work/agent-conversation-monitor/PLAN.md`, `BACKLOG.md`, `LOG.md`.

## 2026-09-15 — stale test suite cleared (merged)

`npm test` had a long-standing red baseline (56 failed / 225 passed / 1 skipped across 7 files) that made the suite untrustworthy as a signal — real regressions would have been invisible in the noise. Went through all 56 individually against current `src/` and git history (not error-text pattern matching) rather than trusting an earlier triage at face value; it held up, but 3 additional stale-UI-text failures surfaced during verification that the triage hadn't listed (a stale "💭 Processing…" placeholder, a stale 500ms tool-hide-debounce assumption, and a stale "✅ Done" checkmark — all replaced by later commits), and one deletion candidate (a session-takeover test) was inverted into a guard-assertion instead, since the behavior it was probing for was a bug already fixed elsewhere, not dead code. Zero real bugs found. 33 tests fixed in place (renamed/relocated API calls, updated fixtures, added missing async lifecycle calls); 23 deleted for behavior intentionally retired with no replacement assertion possible (a JSONL-delta tracking subsystem and manual session-titling/deletion, both removed by earlier refactors) — each tied to a specific retiring commit in the detailed log. Also found and documented (not fixed — it's a `package.json`/tooling change, out of scope for a `tests/`-only task) that `npm test` silently depends on a prior `npm run build`: `tests/cli-agent.test.ts` spawns `dist/cli.js`, and without a build step 7 of its tests fail in a way indistinguishable from a real regression at a glance. Proposing a `pretest` script for the integration owner to pick up.

Verified on branch `test/stale-test-cleanup` before merge: `rm -rf dist && npm run build && npx vitest run` → 0 failed / 259 passed / 1 skipped across all 17 files, re-confirmed after rebasing onto `origin/main` (post `systemd-unit-tracking` merges). No CI runs on this repo's PRs, so that local run was the only signal available. The proposed `pretest` fix was actioned before merge rather than deferred: `package.json`'s `test` script is now `npm run build && vitest run` (commit `cad851a`), chosen over a `pretest` hook so the build step is visible in one line and behaves identically under npm and pnpm; verified by reproducing the 7 `cli-agent.test.ts` failures from a clean `rm -rf dist` and then passing. Integrated via [PR #4](https://github.com/botverse/tgcc/pull/4), merge commit `d3a73cadda0f07d7a9440e896bb8b2cb1c0c4dbc`, merged 2026-09-16, after the 23 deletions were reviewed. This records integration only, not deployment: the suite is green on `main` as of that commit, and nothing here changed `src/` or runtime behaviour. Details: `work/stale-test-cleanup/LOG.md`, `work/stale-test-cleanup/PLAN.md`.

## 2026-09-15 — systemd unit brought under version control (merged)

The `tgcc` systemd user unit crash-looped 2435 times earlier today (`status=127`, missing `libllhttp.so.9.3`) because `ExecStart` pinned a Homebrew Cellar path that a `brew upgrade` invalidated. It was fixed on-host to use the stable brew symlink (`/home/linuxbrew/.linuxbrew/bin/node`), but that fix existed only as an untracked file — nowhere in Git. This change adds `systemd/tgcc.service` to the repo (content unchanged from the fixed live file, verified byte-identical and free of secrets) and points `~/.config/systemd/user/tgcc.service` at it via symlink, so future edits go through Git and the fix isn't lost again. Verified no service restart occurred (`MainPID`/`NRestarts`/`ActiveEnterTimestamp` unchanged across the change). Risk: the live service now depends on this repo's checkout staying at `/home/fonz/Botverse/tgcc` with `systemd/tgcc.service` present, and a future `git checkout`/`reset` can change what the live service runs. Details: `work/systemd-unit-tracking/LOG.md`.

Merged via [PR #1](https://github.com/botverse/tgcc/pull/1), merge commit `f96fb0768c529ac71b576ac1e702320386a3514c`, 2026-09-15T11:49:33Z. What this confirms: the unit is tracked in Git and the live symlink resolves into the repo, and the running service was not restarted by this change (`MainPID` 549257 / `NRestarts` 2435 unchanged throughout, re-verified after merge). This is not a deployment or restart-tested claim beyond that — the service has not been restarted against the symlinked unit since this landed.
