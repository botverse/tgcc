### Key design decisions (not spelled out verbatim in the plan — documenting reasoning)

1. **Capture split between `queueForChat` and `sendToCC`.** `queueForChat` (called only for Telegram-sourced messages, before batching/roster-injection) captures full sender identity (name/handle/id/chat type/title) — this is richer than what survives into `sendToCC`'s already-batched `data.text`. `sendToCC` is the generic capture point for everything else (cron/ralph/supervisor/cli), guarded so it never double-captures a turn a more specific caller already mirrored (new `alreadyMirrored` flag on `source`).
2. **`tgcc_send` origin tracing is single-hop by design**, matching the plan's own "origin unknown is itself information" framing: `resolveOriginHuman(sourceAgentId)` looks at that agent's own most-recently-recorded turn origin and returns it verbatim if it's a Telegram human, else `'unknown'` — it does not chase through a second `tgcc_send` hop. Exclusion is applied consistently: a `tgcc_send` traced back (one hop) to the owner is excluded the same as a direct Telegram turn from the owner would be; an unresolvable origin is never excluded (fails open toward visibility, since silently dropping unattributable traffic would be worse than showing it tagged "unknown").
3. **Coalescing granularity = one `assistant` event.** `--include-partial-messages` means CC emits both fine-grained `stream_event` deltas (already used by `StreamAccumulator` for live TG rendering) AND a complete `assistant` event once a message is fully assembled (confirmed in `cc-process.ts` — `this.emit('assistant', event)` fires with the full `content` array including complete `tool_use.input`). Flushing per `assistant` event already satisfies "flush on message_stop" from the plan; since there's no coarser buffering boundary in this design, "destructive tool calls flush immediately" falls out for free rather than needing a separate urgency code path. `tool_result` events are buffered (not flushed alone) and piggyback onto the next `assistant` flush or turn end, so a tool call immediately followed by its result doesn't produce two separate TG messages.
4. **The 429 retry-with-sleep in `doSend`** mirrors the exact idiom already used in `streaming.ts` (`_doSendOrEdit`): `await sleep(retryAfter * 1000)` then retry, capped at 5 attempts. This is data-driven by Telegram's own response, not a batching/state-transition heuristic, so it doesn't fall under the repo's "no timers for state transitions" rule — same reasoning applies to the per-agent send chain (`sendChains`) not being the kind of cross-agent queue the "no queues" feedback targets: it drains eagerly as each item settles and never waits on the *monitored agent's* state.
5. **`sendCronMessage` helper**, used by all 8 existing call sites that fire cron jobs (`(agentId, text) => this.sendToCC(agentId, { text })` / `(aid, text) => ...`), so cron-triggered turns get the plan's `⏰ cron` tag instead of falling into the generic `🧭 supervisor` bucket. Same treatment was *not* extended to every heartbeat/watcher/tgcc_session call site — see BACKLOG.md "Open" for the reasoning (none of the 11 acceptance criteria depend on it, and `🧭 supervisor` is itself a listed tag in the plan's table, not just a fallback).
6. **Ralph-specific tagging investigated and deliberately not wired further**: `WatcherManager`'s `sendToCC` callback always targets the *watcher* (ralph itself), never the watched target — ralph agents aren't in `monitor.agents` in the plan's example config, so there's currently no path where a monitored agent receives a ralph-tagged turn. Left a note in BACKLOG.md for if that changes.
7. **Redaction fails closed, not open**: if a redaction rule ever throws (shouldn't happen with static patterns, but defensively), `redactSecrets` returns `'[REDACTION FAILED — content withheld]'` rather than the raw text, since leaking a real credential into the monitor group is worse than a dropped mirror line.

### Bugs found and fixed during self-verification

- Generic secret-assignment redaction regex required a literal `_` before `KEY`/`_SECRET` but not before `TOKEN`/`PASSWORD`, so `DB_PASSWORD=...` and `API_TOKEN=...` weren't redacted (`AWS_SECRET_ACCESS_KEY` happened to work by coincidence via the more specific AWS rule). Fixed by moving the optional underscore into the shared prefix character class (`[A-Za-z0-9_]*(?:KEY|SECRET|TOKEN|PASSWORD)`) instead of duplicating it per-suffix. Caught by the scratch harness, not by manual inspection — glad I wrote fixtures for every named category in the plan rather than trusting the regex by eye.
